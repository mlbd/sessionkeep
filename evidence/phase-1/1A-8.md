## Problems found while building, and fixes

1. **Console garbage.** The first walkthrough showed match markers (`«` `»`), the ellipsis and the long dash as unreadable characters once output passed through a Windows code page. Command output now uses plain ASCII for its own text: matches are marked `**like this**`, `...` and `-` replace the typographic characters. User text is still stored and shown unchanged.
2. **Misleading hint.** "read a full record with …" was printed even when nothing was found. It is now shown only when there are results.
3. One generated edit corrupted two Go files (escape sequences); they were restored from git and rewritten. No committed state was affected.

## What is and is not built

- Search covers stored conversation text only: prompts, replies, compaction summaries, tool errors and (at `extended` level) tool output snippets. Instructions are not in this search; they have their own commands.
- Ranking is the full-text engine's relevance score; no recency or importance weighting, no semantic search.
- A query is "all these words". If that finds nothing, the whole query is tried as one literal string. Literal matching ignores case for ASCII letters only.
- Filters: who said it, since/until, limit (maximum 50). `--kind` from the plan was implemented as `--who`.
- `memory get` and `evidence get` are the same lookup in this phase; there are no derived "memories" yet.
- Search opens the database read-only and takes no lease. If the schema does not match the binary it stops and asks for `sessionkeep setup`.

## Not run / limits

- `go test -race` not run (no C compiler). windows/amd64 only; other targets compile.
- Search speed was not measured in this slice (Phase 0 measured the engine at 100k rows; this code path has not been benchmarked).
- Literal search scans the project's text; its cost grows with the amount stored.
- Whether Claude picks the `recall` skill at the right moments, and uses results as evidence rather than instructions, is untested.
