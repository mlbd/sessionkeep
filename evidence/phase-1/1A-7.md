# Phase 1A-7 evidence — durable instructions and recall into sessions

Date: 2026-11-19/20. Machine: reference Windows 10 Pro 22H2 x64. Claude Code 2.1.328. Real runs; nothing mocked. One live session was run (reported cost USD 0.033). User name replaced by `<USER>`, generated ids by `<ID>`.

## Live session: are injected instructions followed?

Sandbox data directory and generated plugin in the session's temporary scratch area (outside the repository; the real per-user data directory was not created). One synthetic project registered. Two instructions recorded:


Command: `claude -p "Name a colour. A one-word answer is fine." --plugin-dir <scratch>\plugin --setting-sources project --strict-mcp-config --no-session-persistence --model sonnet --output-format json`

Both the global and the project instruction were followed in a session that had never seen them, and the exchange was captured. This is one session, one model, two short instructions; it shows the mechanism works, not how reliably a long or conflicting set is followed.

## Defects found by tests in this slice, and fixes

1. **Instructions recorded in the same second came back in random order.** `TestTwentyInstructionsAreRecalledVerbatimInANewSession` failed ("instruction 3 is out of order"): creation times were stored to the second and ties fell back to the random id. They are now stored with fixed-width nanosecond precision.
2. **A file being replaced can look missing to a reader.** The verification gate failed intermittently in `TestReplaceWhileReading`. A measurement run showed that on this machine, in about one run in four, readers saw "file not found" for up to 65 ms during a replace even though the POSIX rename itself succeeded (0 rename failures in 2,000). For a hook that means "no roots cache → no project registered → capture nothing", silently. Fix: every atomically written file now has a second copy written right after the first (`<name>.alt`); a reader that cannot find the first uses the second. The replace test then passed 12 runs in a row. Cause of the window (filesystem behaviour, antivirus or indexer) was **not** diagnosed.

## Scope of this slice — what is and is not built

- Scopes implemented: **global** and **project**. Branch, task and session scopes exist in the schema but have no commands and are not injected.
- **Conflict detection is not built.** The only check is refusing the identical active text twice in one scope. Two instructions that contradict each other are both injected; nothing flags it.
- Recall is from the cache only; if it is damaged, the session is told instructions could not be read (and `sessionkeep setup` rebuilds it).
- Instructions are injected at every SessionStart and, on a prompt, only when the set changed since it was last sent in that session. The assumption that Claude Code re-runs SessionStart after compaction comes from the documentation and was not observed live.
- A paused or `off` project still receives its instructions (recall is separate from capture).
- Text that looks like it contains a secret is refused rather than redacted, because instructions are replayed word for word.
- One instruction is limited to 4,000 characters. Ordering is global first, then project, oldest first; there is no priority setting.
- `sessionkeep remember` is a terminal command; nothing yet lets Claude record an instruction on the user's behalf (no skill, no MCP tool).

## Not run / limits

- `go test -race` not run (no C compiler). windows/amd64 only; other targets compile.
- Interactive mode, compaction and resume not exercised live. Coexistence with other plugins that also inject at SessionStart not tested.
- The `.alt` second copy means a deleted primary file is answered from the copy; to truly reset a file both must be removed.
