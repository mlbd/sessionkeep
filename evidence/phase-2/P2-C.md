# Phase 2, part C — import speed and the cost of removing secrets

Date: 2026-11-20 (session 16). Agent: Claude Code (claude-fable-5-2). Windows 10 (amd64), one
machine, wall-clock times of whole commands. Synthetic data only: 64 session files, 200 pieces
of text each (12,800 pieces of about 700 bytes), generated by a throwaway script.

## 1. Question

Part A left the speed of a full history import unmeasured and guessed that one durable write per
piece of text would be the cost. The owner's real history holds about 12,800 pieces.

## 2. Measurements

| Program | Preview (stores nothing) | Import | Runs |
|---|---|---|---|
| 0.4.0 (one transaction per piece) | 5.4 s | 38.2 s, 38.8 s, 39.6 s | 3 |
| + one transaction per session file | 5.4 s | 13.3 s, 13.3 s, 13.3 s, 13.4 s; also 30.0 s, 64.0 s, 74.7 s, 90.6 s | 8 |
| + rules skipped when they cannot match | 0.3 s | 7.8 s, 7.9 s, 8.0 s | 3 |

`redact.Text` on one 700-byte text without secrets: 397,892 ns before, 10,744 ns after
(`go test -bench`, 2,000 and 20,000 iterations).

## 3. Findings

1. **The guess was half right.** Batching took the import from about 39 s to about 13 s.
2. **The larger cost was removing secrets**, not writing: seventeen regular expressions ran over
   every piece of text, 0.4 ms per 700 bytes. That was the whole 5.4 s of a preview, and it is
   paid by every captured prompt and answer as well, inside the hook.
3. Deciding the project once per folder instead of once per piece changed nothing measurable
   (kept; it is correct and simpler to reason about).
4. **Unexplained:** four of eight runs of the middle variant took 30 to 91 s instead of 13 s.
   The three runs of the final variant did not vary. The cause was not found; nothing was
   running that the agent started. Treat the times as typical, not guaranteed.

## 4. What changed

- `store.IngestEvents`: several events in one transaction, all or none. History import stores
  one session file per transaction. `TestIngestEventsStoresAWholeBatchOrNothing`: a batch with a
  bad event leaves no event and no session behind; a repeated batch is reported as already
  stored.
- `internal/redact`: each rule has a "need", a plain-string test that must hold before its
  expression can match (for example the text must contain `authorization`). Rules whose need
  fails are skipped. Two letters that case-insensitive expressions match but lower-casing does
  not produce (U+017F, U+212A) switch the shortcut off for that text. After any replacement the
  needs are checked against the new text.

## 5. Why the shortcut is safe, and how that was checked

A wrong need would let a secret through, so the result with needs is compared with the result
of running every expression:

| Check | Result |
|---|---|
| `TestNeedsNeverChangeTheResult`: 36 seed texts, each alone, embedded and doubled | pass |
| `FuzzNeedsNeverChangeTheResult`, 90 s, 218,280 inputs | no difference found |
| `FuzzTextIsIdempotent` and the existing fixtures (`TestSecretsAreRemoved`, `TestKnownGaps`) | pass, unchanged |
| Three needs deliberately made too strict | two caught at once; the third (`bearer` followed by a tab or line break) was **not** caught until seed texts for it were added, after which it is |

The fuzz run is short and on one machine. The known gaps of redaction itself
(`TestKnownGaps`) are unchanged by this work.
