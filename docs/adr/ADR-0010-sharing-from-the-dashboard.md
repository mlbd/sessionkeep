# ADR-0010 — Sharing a project is switched on, synced and switched off from the dashboard

- Date / owner / status: 2026-11-22 / project owner / **accepted** (owner: "lets do you all recommendations", after being shown the three choices below). Changes point 6 of ADR-0009.
- Requirement IDs and affected phase: R16–R18 (portability); `docs/06-SYNC_AND_PORTABILITY.md` sections 2, 4 and 6.
- Why: the owner shares only some projects (company work with colleagues) and wants every other project to stay on the computer, wants a colleague who starts later to be able to send everything they have, and wants none of this to need a terminal.
- Decision and constraints:
  1. **Sharing is per project and off by default.** A project is sent nowhere until sharing is turned on for it. This was already so; the dashboard now says it on every project ("Not shared: this project stays on this computer").
  2. **The storage is saved once per computer** (address, bucket, the two keys, the sender's name): Settings, "Cloud storage for shared projects", or `sessionkeep team storage`. The bucket's listing is read to prove the keys work before anything is saved. Saving again replaces the keys for projects that use the same bucket.
  3. **Turning sharing on for a project needs only a shared name and a passphrase.** The passphrase belongs to that shared project, so someone given one project's passphrase cannot read another project in the same bucket.
  4. **One "Sync now" button** (`sessionkeep team sync`) receives what colleagues sent and then sends what is new here. It shows both halves first, with every received instruction in full, and is confirmed once. Push and pull remain as separate commands.
  5. **Keys and passphrases may be typed into the dashboard** (owner-approved change to ADR-0009 point 6, which had them come from the environment only). They travel from the page to the local server in a request body, and from there to the command on its standard input; they are never put on a command line, and no endpoint returns them (changed by D131: a project's passphrase, never a key, is returned after a confirmation). They are stored sealed as before.
  6. **"Stop sharing"** removes the passphrase and the record of what was sent and received from this computer; the bucket and what colleagues received are untouched. Sharing a project under another name or bucket starts its record over.
  7. Sync stays manual. Nothing is sent or received without a press.
- What changed in the trust picture: the dashboard is served on the loopback address only, to one signed-in browser tab, with a request token, an origin check and a strict content policy (ADR-0003). A secret typed there is exposed to what that page and that local server can be made to do, which was not so while secrets came only from the environment. A program already running as the same user could read the environment or the user's files in either design.
- A connection made earlier in a terminal keeps working. While no storage has been saved, the storage of the most recently connected project stands in, so the owner is not asked for the same keys again.
- Evidence: `internal/cli/team_dashboard_test.go` runs two separate data directories through the dashboard's API against a stand-in bucket (a mock that re-computes every signature): sharing refused before storage is saved, wrong keys not saved, short passphrase refused, no answer or settings file showing a secret, preview without effect, one sync in both directions, a second project that was never shared never leaving, a colleague joining later with earlier work, a wrong passphrase, the saved storage used from a terminal, sharing under another name starting over, stop sharing, forgetting the storage. `.tools/smoke_ui.js` presses the four dialogs' buttons by name against stand-in answers.
- Verified against the real service (2026-11-22, by the owner's own connect): Cloudflare R2 accepted the keys and answered a listing with path-style addressing. **Not verified:** an upload to R2, a download from it, and the conditional put; nothing has been uploaded yet. No one has looked at the new screens in a browser.
- Risks accepted: those of ADR-0009, and the one named above.
