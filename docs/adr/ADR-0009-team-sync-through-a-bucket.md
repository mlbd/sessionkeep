# ADR-0009 — Team sync: encrypted bundles in a bucket the owner chose

- Date / owner / status: 2026-11-22 / project owner / **accepted for a first, manual version** (owner: "go ahead with R2", after choosing client-side encryption, sessions included, manual push and pull). Not yet run against a real bucket.
- Requirement IDs and affected phase: R16–R18 (portability), ROADMAP phase 9 (team features) brought forward in a reduced form; `docs/06-SYNC_AND_PORTABILITY.md` sections 2, 4 and 6.
- Decision and constraints:
  1. `sessionkeep team connect|push|pull|status|disconnect` exchanges one project's memory with colleagues through an S3-compatible bucket in the owner's own account (Cloudflare R2 first). No SessionKeep server exists; nothing is sent anywhere until a project is connected and a push is confirmed.
  2. What travels is a **bundle**: the same content and the same field-by-field checks as a handoff file (D120) — the project's own instructions, checkpoints, prompts and replies — holding only what this computer has not sent before and nothing it received from others. Folders are shortened and the secret rules run again before sealing, and once more on the way in.
  3. A bundle is compressed and then encrypted on the sending computer with a passphrase the team shares, in the **age** format (`filippo.io/age` v1.3.2, BSD-3-Clause; scrypt passphrase recipient, its default work factor). No cryptography of our own. The passphrase must be at least 12 characters.
  4. Bundles are immutable and named by time, sending computer and a random part; a put is conditional (`If-None-Match: *`), so nothing in the bucket is ever replaced and two people may push at once. There is no shared "latest" pointer, hence no conflict to resolve: receiving merges by record id and receiving twice adds nothing.
  5. Push and pull each show what would happen and need `--yes` (in the dashboard: a second press). Pull prints every received instruction in full first, because it becomes text Claude is told every session.
  6. (Changed by ADR-0010: they may also be typed into the dashboard.) The storage keys and the passphrase are read from the environment for `team connect` only — never from the command line, never through the dashboard — and stored sealed with the Windows Data Protection API for the signed-in user. On other systems they are kept in a file only the user can read, and the command says so.
  7. The S3 client is our own minimal one (put, get, list; Signature Version 4; path-style addressing), not an SDK: about 250 lines against a dependency tree of dozens of modules.
- What the storage service can and cannot see: it cannot read any text. It can see the number of bundles, their sizes, the time of each push and a 10-character tag of the sending computer. The shared project name is hashed in object names.
- What this does not do: move code (Git does), continue a colleague's Claude Code session, sync automatically, delete from the bucket, or take back what a colleague already received. Removing someone's access means revoking their storage key and, for future bundles, changing the passphrase under a new shared name.
- Evidence: `internal/s3lite` reproduces the four worked signatures of Amazon's "Signature Calculations for the Authorization Header" examples; `internal/team` tests wrong passphrase, altered bytes and non-bundles; `internal/cli/team_test.go` runs two, then four, separate data directories against a stand-in bucket (a mock that re-computes every signature): preview without effect, exchange in both directions, a session that grows, a wrong passphrase, a wrong storage secret, an altered bundle, and that the bucket's contents and object names hold none of the text.
- Not verified: **no request has been made to Cloudflare R2.** Path-style addressing is not stated in R2's documentation (read 2026-11-22) and is assumed from common use; R2's documented region `auto`, conditional put and ListObjectsV2 support are relied on as documented. Prices and free allowances were read on the same day (10 GB-month, 1 million class A and 10 million class B operations a month, no egress charge) and will change. A real bucket test by the owner is the acceptance check.
- Risks accepted: a weak or leaked passphrase exposes every bundle ever stored under that name; the passphrase cannot be rotated in place; a colleague who leaves keeps what they received; an attacker with write access to the bucket can add bundles only if they also know the passphrase (age authenticates), and can delete bundles (not detected).
